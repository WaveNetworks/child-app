# mobile-shell — Cordova shell TEMPLATE

Not a working project. This is the source the provisioner copies out to create
`WaveNetworks/<slug>-cordova` when an app is provisioned with mobile enabled.

Every `__PLACEHOLDER__` is substituted at that point:

| placeholder | example |
|---|---|
| `__APP_NAME__` | `Northwind` |
| `__APP_SLUG__` | `northwind` |
| `__APP_DOMAIN__` | `northwind.com` |
| `__APP_BUNDLE_ID__` | `com.wavenetworks.northwind` |
| `__APP_DESCRIPTION__` | one line, from the spec |
| `__APP_BRAND_HEX__` | `2D6FC4` — no leading `#` |
| `__CAPAWESOME_APP_ID__` | the Capawesome Cloud app UUID |

## What the shell is for

It is a **dumb build target**. `www/` is generated by the app's own
`scripts/release-mobile.sh` (which execs core's), so this repo holds only the
native wrap: `config.xml`, the pinned plugin list, the build-number hook, and the
icon/splash assets.

`www/` is gitignored here on purpose. Committing it would recreate the second
copy of every screen that the whole wet-markup/dry-behavior split exists to
avoid.

## Icons and splash

`res/` is generated at provision time from the app's uploaded branding, so it is
not part of the template. A build needs:

```
res/icon/android/ic_launcher.png             432x432
res/icon/ios/icon-1024.png                   1024x1024
res/screen/android/splash-port.png           1280x1920
res/screen/ios/Default@2x~universal~anyany.png  2732x2732
```

## Two things that are easy to get wrong

1. **The first store submission must include `@capawesome/cordova-live-update`.**
   A release shipped without it can never receive an OTA update — the capability
   cannot be added to binaries already on devices.
2. **`DEFAULT_CHANNEL` is rewritten by `release-mobile.sh` on every build.** Do
   not hand-edit it. Pinning the channel to the binary version is what stops a
   bundle reaching an app that cannot run it.

See `docs/MOBILE.md` in this repo, and the ops box's signing-vault notes for
where the signing material lives.
